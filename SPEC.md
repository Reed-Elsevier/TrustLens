# SPEC.md: Trust Lens Integrity & Legal Insights Platform

## 1. Project Description

A single Next.js web application with two analysis modules that share one SQLite database, one auth layer, one AI layer and one UI shell:

- **Module A: Publishing Integrity.** Surfaces suspicious manuscripts and reviewer behaviour before publication.
- **Module B: Legal Research Assistant.** Answers legal research questions and tracks how well legal content is kept up to date.

Every question below ends as a real number or table on screen, computed from the provided CSV data. AI is a core part of the product: it routes questions, explains results and summarizes evidence, while all figures come from SQL or code.

**Stack:** Next.js (App Router, TypeScript), SQLite, NextAuth, AWS EC2.

## 2. Problems and Target Questions

### Module A: Publishing Integrity
Goal: spot suspicious manuscripts and review behaviour before publication.

Key tables: `manuscripts`, `peer_review_assignments`, `research_papers_published`, `citations`, `authors`, `institutions`, `research_integrity_flags`

| # | Question | Output on screen |
|---|----------|------------------|
| A1 | Which reviewers keep reviewing each other's work, and how fast and how positively? | Ranked table of reciprocal reviewer pairs with count, average turnaround and average score or recommendation |
| A2 | Are there groups of papers with near-identical abstracts? | Clusters of papers with a similarity score and a side-by-side abstract view |
| A3 | Which signals best predict an integrity flag? | Ranked signals showing how strongly each one predicts `research_integrity_flags` |

### Module B: Legal Research Assistant
Goal: answer legal research questions and keep content up to date.

Key tables: `legal_documents`, `legal_citations`, `regulatory_updates`, `regulatory_update_impacts`, `editorial_tasks`

| # | Question | Output on screen |
|---|----------|------------------|
| B1 | Is a given case still good law? | Search for a case, then show its citing cases with treatment and a verdict |
| B2 | Which jurisdictions miss the 72-hour update deadline most? | Jurisdictions ranked by miss rate, with counts and median delay |
| B3 | Did the auto-classification pilot improve outcomes, or only speed? | Before/after (or pilot/control) comparison on speed and on outcome quality |

## 3. Architecture

### 3.1 Principles
1. **Numbers come from SQL or code, never from the LLM.** The LLM explains, routes and summarizes. It does not calculate.
2. **Feature folders, not type folders.** Everything for Module A lives under `features/integrity`, everything for Module B under `features/legal`.
3. **Three layers per feature:**
   - **Route handler** (`app/api/...`) parses the request, calls a service, returns JSON. No logic.
   - **Service** (`features/<x>/service.ts`) holds the analysis logic and combines queries.
   - **Repository** (`features/<x>/repository.ts`) holds the SQL only.
4. **Pages only render.** Pages fetch from the API or call services in server components. They never contain SQL.
5. **Shared code goes in `lib/`, and only after two features need it.**

### 3.3 Database
- SQLite file at `data/app.db`, opened via `better-sqlite3` with raw SQL. No ORM, since the data is read-only analytics.
- `scripts/import-csv.ts` creates one table per CSV, taking column names from the header row and inferring types. Indexes go on foreign keys and date columns right after import.
- In production the DB is opened **read-only**. The app never writes to the analysis tables.

### 3.4 Auth
- NextAuth (Auth.js) with a **Credentials provider and one demo user from env vars**. No sign-up flow and no user table.
- `middleware.ts` guards `(protected)/*`.

### 3.5 Deployment (AWS)
- **A single EC2 (or Lightsail) instance running the app in Docker**, with the SQLite file on the instance disk.
- Serverless options (Lambda, Amplify) are avoided because `better-sqlite3` is a native module and serverless filesystems are ephemeral or read-only.
- Deploy an empty app behind login early, then redeploy after each milestone.

## 4. AI Integration (candidates, decision pending)

Ranked from highest to lowest value-to-effort:

1. **Natural-language assistant over fixed analysis tools.** The user asks a question in plain English. The LLM picks a function from `lib/ai/tools.ts` (e.g. `getReciprocalReviewers`, `checkCaseTreatment`), the service runs real SQL, and the LLM narrates the result. Fixed tools are safer and faster than free-form text-to-SQL.
2. **Explain-this-flag summaries (Module A).** For a flagged manuscript, feed the structured evidence (reviewer overlap, abstract similarity, citation pattern) to the LLM and get a short reviewer-facing explanation.
3. **Legal treatment summary (Module B).** For a case, summarize how citing cases treat it, using the citations returned by SQL, so the verdict is explained and not just stated.
4. **Regulatory update classification (Module B).** Classify `regulatory_updates` by impact area, which also gives a natural way to frame B3.

Constraints:
- Provider is not decided yet. `lib/ai/client.ts` exposes a single `ask()` function so the provider can change in one file.
- Every AI answer shows the underlying numbers or rows next to the text.
